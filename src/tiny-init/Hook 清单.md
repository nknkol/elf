### 第一类：身份切换与组管理 (必须 Hook，否则程序会挂)

这类调用通常需要 `root` 权限。在非特权容器中，真实内核一定会拒绝它们。
**现在的策略（Phase 1 & 2）：** 必须拦截，并**假装成功 (Return 0)**。

| 系统调用 | 作用 | 为什么必须 Hook？ | 现在的处理逻辑 (Phase 1/2) | 未来的逻辑 (Phase 3) |
| :--- | :--- | :--- | :--- | :--- |
| **`setuid` / `setgid`** | 设置UID/GID | 普通用户无法切换 ID，内核直接拒。 | **直接返回 0** (假装切换成功)。 | 更新共享内存中的 vPCB 表。 |
| **`seteuid` / `setegid`** | 设置有效ID | 同上。 | **直接返回 0**。 | 更新 vPCB 的 euid/egid 字段。 |
| **`setreuid` / `setregid`** | 同时设R/E ID | 同上。`su` 命令严重依赖此调用。 | **直接返回 0**。 | 更新 vPCB。 |
| **`setresuid` / `setresgid`** | 设置R/E/S ID | 同上。最完整的身份设置调用。 | **直接返回 0**。 | 更新 vPCB。 |
| **`setfsuid` / `setfsgid`** | 设置文件系统ID | 主要用于 NFS 或特定服务。 | **直接返回 0**。 | 很少用，通常跟随 `setuid` 更新即可。 |
| **`setgroups`** | 设置附属组 | 需要 `CAP_SETGID`，普通用户必败。 | **直接返回 0**。 | 更新 vPCB 中的 groups 列表。 |
| **`initgroups`** | 初始化组列表 | **注意：这是一般是库函数**。 | 通常它底层调用 `setgroups`。只要 Hook 了 `setgroups`，这个自然就“成功”了。 | 同上。 |

**警告：** 如果不 Hook 这些，`apt` 在降权到 `_apt` 用户时会崩溃，`sudo` 也会直接报错退出。

### 第二类：信息查询 (必须 Hook，否则露馅)

| 系统调用 | 作用 | 为什么必须 Hook？ | 处理逻辑 |
| :--- | :--- | :--- | :--- |
| **`getgroups`** | 获取附属组 | 真实内核返回的是你宿主机的组（可能是一堆乱七八糟的 Android/鸿蒙 GID）。 | **返回 0 (无)** 或者 **返回 `root` 组**。不要透传给内核。 |

### 第三类：进程关系与会话 (建议 Hook，视需求而定)

这类调用不像上面那么致命，但在容器化环境中，为了“像真的 Linux”，通常也需要处理。

| 系统调用 | 作用 | 分析与建议 |
| :--- | :--- | :--- |
| **`getpid()`** | 获取 PID | **可以暂不 Hook (透传)**。<br>虽然 PID 可能是 12345 而不是 1，但大多数程序不关心 PID 的绝对值。只有当你需要实现 PID Namespace（让 `ps` 只显示容器内进程，且 init 为 1）时才需要由 Payload 维护一张 `Real PID <-> Virtual PID` 的映射表。 |
| **`getppid()`** | 获取父 PID | **强烈建议 Hook**。<br>如果不 Hook，容器内 PID 1 (Init) 的父进程会显示为 Loader 的 PID。程序会觉得奇怪：“我明明是 Init，为什么我有爸爸？”<br>**逻辑：** 如果当前是容器 Init 进程，返回 `0`；否则透传。 |
| **`setsid()`** | 创建新会话 | **建议 Hook 并假装成功**。<br>如果当前进程已经是进程组组长，真实调用会失败。为了保证服务（Daemons）能正常后台运行，通常拦截并返回当前 PID（模拟成功）。 |
